## 1. `BuildWorkflowMap` use-case — orchestration order + interfaces

`packages/application/src/semantic/BuildWorkflowMap.ts`. A thin orchestrator: it owns the **order** and the
**budget reset**, delegates every step to an injected, already-built collaborator, and assembles the one finalized
`WorkflowMap`. It imports **only** domain types + application collaborators — never an adapter/SDK (NFR1).

### Orchestration order (and why)

```
execute(runId): Promise<WorkflowMap>
  0. budget.reset()                                  // one shared counter, fresh per run (§4)
  1. graph = await stateGraphRepository.findByRunId(runId)
       graph == null || graph.nodes.size === 0  ⇒  return emptyMap(runId)      // NFR6, edge case
  2. { workflows, /*orphanStateIds*/ } = extractor.extract(graph)              // #54 pure, rule-based
  3. intent  = await inferIntent.execute(graph)                                // #55 a11y-first, budgeted LLM
  4. refined = await refineIdentities.execute(graph, intent)                   // #58 post-hoc embedding pass
       → refined.canonicalMap (CanonicalIdentityMap), classes, embeddingCallCount
  5. detected = duplicateDetector.detect(workflows, refined.canonicalMap, intent)   // #58 pure
       → detected.workflows (isHiddenPath set on hidden routes), detected.duplicateGroups
  6. named = await nameAndGroup.execute(detected.workflows, intent)            // #56 budgeted LLM, relabel-only
       → named.workflows (name/description/featureGroup/inferenceConfidence), appPurpose, appPurposeConfidence
  7. return {
       runId, finalisedAt: clock.nowIso(),
       workflows: named.workflows,
       appPurpose: named.appPurpose,
       appPurposeConfidence: named.appPurposeConfidence,
       duplicateGroups: detected.duplicateGroups,                              // §3 additive
     }
```

**Why this order is the only correct one:**

- **Extraction first** — everything downstream consumes `Workflow[]`/the graph; it is pure and deterministic.
- **Intent before refine AND before grouping** — `RefineIdentities` consumes intent for its **confident-label veto**
  (`labelsFromIntent`), and `SemanticDuplicateDetector` + `NameAndGroupWorkflows` both consume the same `IntentModel`.
  Inferring it once (one pass) keeps the budget honest and the inputs consistent.
- **Refine (produces the canonical map) before detect** — the detector's whole job is to read
  `canonicalMap.get(rawOutcome)`; the map must exist first. This is **where the canonical map is applied** (§2).
- **Detect before grouping** — the detector sets `isHiddenPath` on the hidden routes; `NameAndGroupWorkflows` is the
  **last** relabeling pass and copies `id`/`steps`/`isHiddenPath` through unchanged (its authoritative-set invariant,
  spread on `...workflow`). Running detect first means the **final** workflow objects already carry `isHiddenPath`.
  (Order is field-safe either way — grouping never reads or drops `isHiddenPath` — but detect→group keeps the
  hidden-flag on the objects grouping emits, with no second copy pass.)
- **`duplicateGroups` is map-level**, untouched by grouping, so it is captured from step 5 and attached at assembly.

Cardinality/determinism are preserved end-to-end: extraction is deterministic, detect returns `workflows.map(...)`
(same order/count), grouping iterates input order (same order/count). Same graph + same fakes ⇒ deep-equal map (NFR2).

### Constructor (DI — all collaborators are pre-built abstractions)

```ts
class BuildWorkflowMap {
  constructor(
    private readonly stateGraphRepository: StateGraphRepository, // domain port (AppPorts)
    private readonly extractor: WorkflowExtractor, // #54
    private readonly inferIntent: InferIntent, // #55
    private readonly refineIdentities: RefineIdentities, // #58
    private readonly duplicateDetector: SemanticDuplicateDetector, // #58
    private readonly nameAndGroup: NameAndGroupWorkflows, // #56
    private readonly budget: RunBudgetMeter, // §4 — shared across 3/5/6
    private readonly clock: () => string = () => new Date().toISOString(),
  ) {}
}
```

`emptyMap(runId)` returns `{ runId, workflows: [], finalisedAt, appPurpose: undefined, appPurposeConfidence:
undefined, duplicateGroups: [] }` — a valid, well-formed map for an empty/single-node/disconnected graph (no crash).
**Resilience (NFR6):** the three async passes (#55/#56/#58) already degrade internally (tier-1 / a11y-only / null
confidence) and never throw on inference failure; `BuildWorkflowMap` adds **no** try/catch around them because each
guarantees a present result. The only defensive boundary is the `graph == null` check. Exactly one map is always
returned.

## 2. CanonicalIdentityMap wiring — DECISION: purely POST-HOC inside `BuildWorkflowMap`; `collaborators.ts` is NOT touched

**The obligation (coordinator comment on #59):** "#59 capstone MUST wire the `CanonicalIdentityMap` produced by the
post-hoc embedding pass into the composition root / `collaborators.ts`."

**Decision — the map is wired/consumed, but POST-HOC inside `BuildWorkflowMap` (step 5), and the live crawl's
`collaborators.ts` is left exactly as #57 shipped it (exact-E2 identity, no map).** Rationale (ADR-0005 §4.4 is
explicit that refinement is post-hoc over the **finalized** graph):

- **The map is a product of the crawl's own output.** `RefineIdentities` walks the **finalized** `StateGraph` and
  emits the `CanonicalIdentityMap`. During the live crawl that map **does not yet exist** — you cannot feed a node's
  identity a map derived from a graph that node is still being added to. Wiring it into `collaborators.ts`'s
  `CompositeStateIdentityStrategy` (the optional read-only seam #57 reserved) would be wiring an **empty** map on
  every real run; it can only ever be non-empty on a _subsequent_ crawl of the same app version — which is cross-run
  priming, i.e. **E7** (persistence/diffing), explicitly out of E3 scope. Wiring it now = YAGNI + dead code.
- **The correct consumer of a post-hoc map is the detector, not the live `identify`.** `SemanticDuplicateDetector`
  applies the map by mapping each workflow's **raw outcome** → **canonical outcome** (`canonicalMap.get(rawOutcome) ??
rawOutcome`) and flagging the cross-identity convergence. That **is** the merge running. Step 4→5 of
  `BuildWorkflowMap` is the wiring; the epic success metric (surface ≥1 hidden/duplicate path) is realized there.
- **Workflows keep raw step `stateId`s** (E4 renders the actual screens visited); only the **outcome grouping** uses
  canonical ids (carried on `DuplicatePathGroup.outcomeIdentity`). Re-keying the whole graph through a
  composite-with-map would force re-extraction with zero added value to the `WorkflowMap`/E4 contract.

**This discharges the tracked obligation explicitly:** the `CanonicalIdentityMap` IS wired into the live pipeline —
inside `BuildWorkflowMap`, into the detector — which is where a post-hoc map belongs. `collaborators.ts`,
`StartCrawlRun.ts`, and `CompositeStateIdentityStrategy`'s seam are **unchanged**. No `CrawlBudget.maxEmbeddingCalls`
lever is added (ADR-0005 §5 deferred it; §4 below shows the fold-in suffices). The seam #57 reserved on the composite
stays dormant until E7 wants cross-run priming — recorded as the activation point, not deleted.

> **Gate note for arch-review:** if a reviewer expects a `collaborators.ts` diff, this section is the resolution —
> absence of that diff is **correct**, not a missed obligation.

## 3. `WorkflowMap.duplicateGroups?` — additive shape (deferred from #58)

Add ONE optional field to `packages/domain/src/models/workflow.ts` (`DuplicatePathGroup` already exists & is exported;
no other domain change):

```ts
export interface WorkflowMap {
  readonly runId: string;
  readonly workflows: readonly Workflow[];
  readonly finalisedAt: string;
  readonly appPurpose?: string; // #56 / ADR-0007
  readonly appPurposeConfidence?: ConfidenceScore | null; // #56 / ADR-0007
  /**
   * NEW (#59). The semantic cross-identity convergence relations (E3.5/#58). E4 renders
   * "these N paths reach the same place"; the per-route flag is the existing Workflow.isHiddenPath.
   *   - omitted/undefined ⇒ pre-#59 map (back-compat).
   *   - []                ⇒ #59 ran detection, found no semantic duplicates.
   *   - non-empty         ⇒ one group per qualifying cross-identity outcome.
   */
  readonly duplicateGroups?: readonly DuplicatePathGroup[];
}
```

**Additive-only** (optional field, mirrors the `appPurpose` semantics ADR-0007 established): no existing field
changes, no break to E4's current build. It is the **E4 consumer contract for duplicates** — flag to the
arch-review gate as a sanctioned additive domain change (ADR-0005 memory already listed it as #59-owned, OQ3-adjacent).
`isHiddenPath` stays the per-`Workflow` flag; the cross-workflow relation lives on the map, never on the entity
(per `duplicate-path.ts`'s own design note — avoids entity bloat / sibling coupling).

## 4. Shared cross-pass budget — DECISION: one `RunBudgetMeter` injected into all three passes' guards

**Problem (deferred from #58):** three passes spend against `CrawlBudget` — intent tier-2 (#55, `IntentBudgetGuard`),
naming/purpose (#56, _reuses_ `IntentBudgetGuard`), embedding (#58, `EmbeddingBudgetGuard`). Today each guard keeps
its **own** `_callsUsed`/`_tokensUsed`. #55 and #56 already collapse if handed the **same** `IntentBudgetGuard`
instance — but #58's `EmbeddingBudgetGuard` is a separate class with separate counters, so total spend is **not**
globally bounded: each pass can independently spend up to `maxLlmCalls`/`maxTokens`. A structural-substitution trick
(`RunBudgetMeter` masquerading as both guards) is **impossible** — both guards have `private` fields, so TS compares
them nominally; a different class is not assignable to the guard param types.

**Seam (minimal, additive — the cleanest correct option):** introduce ONE shared counter and have both guards
**delegate** to it.

- **New:** `packages/application/src/semantic/budget/RunBudgetMeter.ts` — the single source of truth over one
  `CrawlBudget`: `canCall(): boolean`, `recordUsage(promptTokens: number, completionTokens?: number): void`,
  `reset(): void`, `get callsUsed`, `get tokensUsed`. Pure, deterministic, no I/O. `canCall()` =
  `callsUsed < maxLlmCalls && tokensUsed < maxTokens`; `recordUsage` clamps negatives to 0 and counts every attempt
  (failures included — T3/T6).
- **Additive edit to `IntentBudgetGuard` (#55) and `EmbeddingBudgetGuard` (#58):** the constructor accepts EITHER a
  `CrawlBudget` (existing path — self-constructs a private meter; **back-compat, every existing guard/refiner test is
  untouched and stays green**) OR a `RunBudgetMeter` (shared path — delegates all four members to it). The two guards
  become thin pass-throughs to the meter. **The refiners/orchestrators (#55/#56/#58) are NOT edited** — they keep
  calling `budget.canCall()` / `budget.recordUsage(...)` against the same nominal guard types.
- **Wiring:** `wire.ts` constructs ONE `RunBudgetMeter` over the run's `CrawlBudget`, passes it to the
  `IntentBudgetGuard` injected into #55's `LlmIntentRefiner` and #56's `LlmNamingRefiner`+`AppPurposeInferer`, and to
  the `EmbeddingBudgetGuard` injected into #58's `RefineIdentities`. All three passes now draw on the **same** counter.
- **Per-run isolation:** `BuildWorkflowMap.execute()` calls `budget.reset()` first (step 0). This matches E2's
  wire-once `StartCrawlRun` precedent (the engine is built once; per-run state is reset, not reconstructed). See R-2.

**Effect:** total LLM + embedding spend across the whole `BuildWorkflowMap` run is bounded by ONE
`maxLlmCalls`/`maxTokens` ceiling — the assertion in §6. No `maxEmbeddingCalls` knob (ADR-0005 §5 / §2 above; YAGNI).

## 5. #54 orphan should-fixes — DECISION: leave as tracked debt; do NOT fix in #59

The code-reviewer flagged two `WorkflowExtractor` items for the capstone: (a) orphan-accounting asymmetry under cap
truncation (`visitedNodes.add(edge.toId)` marks a child as "covered" before the cap/recursion decision, so a node on
**no emitted path** can still be excluded from `orphanStateIds`), and (b) an unasserted orphan-under-duplicate-outcome
behavior.

**Recommendation: tracked debt, with a focused follow-up issue — not fixed in #59.** Rationale:

- **No consumer in the `WorkflowMap` contract.** `orphanStateIds` is documented "extractor-internal, not a domain
  field"; `BuildWorkflowMap` does not surface it and the E4 contract has no orphan field. Fixing the asymmetry changes
  **zero observable map behavior** — it is pure internal accounting with no #59 stakeholder. (The PRD's "orphans
  surfaced, not dropped" edge case would mean a _new_ map field — an E4-coordinated additive change outside #59's remit.)
- **Capstone risk discipline.** The whole pipeline's determinism (AC2, NFR2) rests on `WorkflowExtractor`'s DFS.
  Perturbing its `visitedNodes` bookkeeping inside the integration capstone — a serial, broad-surface ticket — risks a
  regression to the one component every downstream pass depends on, for no contract gain. Item (b) is literally a
  **missing test assertion**, best added alongside (a) against #54's own eval fixtures, not bolted onto #59's E2E.
- **Better home.** Both are tight, unit-level refinements with #54's fixtures — a small dedicated "E3 extractor
  orphan-accounting" follow-up gives them their own coverage and review, keeping #59 focused on assembly + the success
  metric. **Action:** the coordinator files that follow-up; #59's E2E does **not** assert on orphan internals (so it
  never silently locks in the asymmetric behavior).

## 6. Composition-root wiring (`wire.ts`) + E2E

### 6.1 `wire.ts` — assemble `BuildWorkflowMap` from resolved ports/adapters (NFR1 / port purity)

`wire.ts` is the only place that names concrete adapters. It already builds `LlmAdapter` + `InMemoryDecisionCache`.
#59 adds (all adapter/impl construction stays here; **`BuildWorkflowMap` itself imports no adapter**):

- **EmbeddingPort:** `new EmbeddingAdapter(embeddingClient, …)` (exists, `packages/adapters/llm` — Voyage default per
  ADR-0005 §4.3). If no embedding-client factory exists yet, add a thin `createEmbeddingClient()` beside
  `createAnthropicClient` (adapter layer — not application). The model id is config-pinned (`EMBEDDING_MODEL`).
- **Caches:** `InMemoryIntentCache`, `InMemoryGroupingCache`, `InMemoryEmbeddingCache` (all exist).
- **Shared budget:** one `RunBudgetMeter` over the run `CrawlBudget` (§4), threaded into the intent/grouping
  `IntentBudgetGuard` and the embedding `EmbeddingBudgetGuard`.
- **Pure collaborators / configs:** `CredentialRedactor`, `A11yIntentDeriver`, `LlmIntentRefiner`,
  `RuleNameStrategy`, `LlmNamingRefiner`, `AppPurposeInferer`, `SamenessRefiner` (+ `defaultSamenessConfig`),
  `projectA11ySkeleton`, `defaultRefineIdentitiesConfig`, `defaultDuplicateDetectorConfig`,
  `defaultExtractionConfig`, `defaultInferIntentConfig`, the grouping config.
- **Assemble** `InferIntent`, `RefineIdentities`, `SemanticDuplicateDetector`, `NameAndGroupWorkflows`,
  `WorkflowExtractor`, then `new BuildWorkflowMap(stateGraphRepository, …, runBudgetMeter)`.
- **Expose** via an `AppContextWithWorkflowMap` extension (mirrors the existing `AppContextWithCrawl.startCrawlRun`
  pattern): `appContext.buildWorkflowMap = buildWorkflowMap`. `AppPorts` is **not** expanded (the embedding adapter +
  caches are composition-internal, like the policy chain) — keeps the port surface minimal.

`StateGraphRepository` comes from the existing `AppPorts.stateGraphRepository`. Secret hygiene: the embedding key, like
the Anthropic key, is read only here and passed via the adapter ctor — never logged/in events (NFR5/T5).

### 6.2 E2E — two layers (per the E2.7 precedent), fakes only, deterministic

**Fixture (new, `test-support/fixtures/`, does NOT edit `capstoneFixture.ts`):** a multi-screen `StateGraph` VALUE with
BOTH:

- a **structural** convergent path — one node reached via ≥2 paths with the **same raw identity** (→ E2's
  `duplicatePathNodeIds`; must **not** be flagged semantic), AND
- a **distinct-identity hidden/duplicate path** — two outcome nodes with **different raw a11y signatures** whose
  fake embeddings are ≥0.94 cosine (the refiner merges them to one canonical) reached via two routes (→ ≥1
  `DuplicatePathGroup`, the less-prominent route `isHiddenPath = true`).
- plus a clean node and a node whose a11y carries a **synthetic** secret/OTP token (redaction assertion).

**Fakes:** `FakeEmbeddingPort` (exists, in `test-support`) seeded so the two same-screen buckets are near-identical and
the genuinely-different outcome is far; a `FakeLlmPort` with synthetic canned responses (intent labels, names/groups,
app purpose — T12, no real identifiers). A tiny `CrawlBudget` (e.g. `maxLlmCalls: 3`) to bite the cap.

**Layer 1 — application capstone** (`semantic/__tests__/BuildWorkflowMap.e2e.test.ts`): drive `BuildWorkflowMap`
directly with the fixture + fakes. **Asserts:**

- **Extraction+grouping:** every reachable outcome appears as a workflow; each workflow has a non-empty `featureGroup`.
- **App purpose:** `appPurpose` non-empty; `appPurposeConfidence` is a `ConfidenceScore` (llm) or `null`.
- **Semantic duplicate (success metric):** `duplicateGroups.length >= 1`; ≥1 workflow `isHiddenPath === true`; the
  flagged one is the **cross-identity** case (its `DuplicatePathGroup` spans ≥2 distinct raw outcomes), and the purely
  **structural** convergent node is **not** in `duplicateGroups` (precision — no double-flag).
- **Confidence-or-null:** every `workflow.inferenceConfidence` is `ConfidenceScore | null`; same for
  `appPurposeConfidence`.
- **Shared budget:** total fake LLM calls + fake embedding calls across all passes ≤ `maxLlmCalls`, and total tokens ≤
  `maxTokens` (one shared ceiling); embedding count == number of **distinct a11y buckets** (one-per-bucket, cache-first).
- **Degraded-safe:** with a `FakeLlmPort` that throws on every call, `execute` still returns exactly one well-formed
  `WorkflowMap` (rule-based names, `null` confidences, `appPurpose: "Unknown"`), no throw.
- **Determinism:** two `execute` runs over the same fixture produce a **deep-equal** map (ids, order, groups).
- **Redaction:** the synthetic secret/OTP token appears in **no** workflow name/description/step, no `appPurpose`, no
  `DuplicatePathGroup`, and was never sent to the fake LLM/embedding port (fakes record their inputs).
- **No real LLM, no simulator** — only fakes; no `MobileDriverPort`, no network.

**Layer 2 — composition-root wiring** (`packages/api/src/__tests__/build-workflow-map.wiring.test.ts`): `buildAppContext()`
exposes `buildWorkflowMap`; assert it is constructed and that the application layer is port-pure (the existing
dependency-cruiser/eslint-boundaries gates enforce no `adapters/*` import from `application` — green is the assertion).
A seeded in-memory `StateGraphRepository` lets it run the pipeline through the wired graph once (smoke), no network.

**Coverage (NFR4, ≥85% line+branch in `application`):** `BuildWorkflowMap` + `RunBudgetMeter` are small and fully
exercised by Layer 1; the additive guard branches (shared-meter vs self-meter) are covered by a focused guard test +
the E2E. Target ≥85% line+branch on the new units; the merged passes keep their existing coverage.

## 7. Acceptance criteria (Given/When/Then)

- **AC1 — assembly & order.** _Given_ a finalized fixture `StateGraph` and the five wired passes, _when_
  `BuildWorkflowMap.execute(runId)` runs, _then_ it returns exactly one `WorkflowMap { runId, workflows, finalisedAt,
appPurpose, appPurposeConfidence, duplicateGroups }` produced in the order extract→intent→refine→detect→group.
- **AC2 — canonical map post-hoc.** _Given_ two outcome nodes with distinct raw identities but ≥0.94 fake-embedding
  cosine, _when_ the map is built, _then_ they converge to one canonical outcome and the less-prominent route is
  `isHiddenPath = true` with a matching `DuplicatePathGroup` — **and** `collaborators.ts`/`StartCrawlRun.ts` are
  unchanged (the merge runs entirely inside `BuildWorkflowMap`).
- **AC3 — precision.** _Given_ a purely structural convergent node (same raw id via ≥2 paths) and two genuinely
  different outcomes, _when_ detection runs, _then_ neither is emitted as a semantic `DuplicatePathGroup`.
- **AC4 — additive contract.** _Given_ the new `WorkflowMap.duplicateGroups?`, _then_ it is optional, defaults to `[]`
  when detection runs and finds none, and no existing `WorkflowMap`/`Workflow` field changes (E4 builds unbroken).
- **AC5 — shared budget.** _Given_ a `CrawlBudget` of `maxLlmCalls: N`, _when_ a run that would otherwise exceed it
  executes, _then_ the **combined** LLM + embedding call count across intent/grouping/embedding is ≤ N (one shared
  ceiling), and the run still finalizes one map.
- **AC6 — degraded-safe / determinism.** _Given_ a fake LLM that always throws (or zero budget), _then_ exactly one
  well-formed `WorkflowMap` is returned (rule-based, null/`"Unknown"` confidences), and two identical runs are
  deep-equal.
- **AC7 — secret hygiene.** _Given_ a node a11y snapshot carrying a synthetic secret/OTP, _then_ it appears in no map
  field and was never sent to any LLM/embedding port (NFR5/T1/T3).
- **AC8 — wiring & purity.** _Given_ `buildAppContext()`, _then_ `buildWorkflowMap` is constructed from resolved ports +
  composition-root adapters, `BuildWorkflowMap` imports no adapter/SDK, and boundaries/cycles stay green.

## Risks

- **R-1 (additive guard edit on merged #55/#58).** Touching `IntentBudgetGuard`/`EmbeddingBudgetGuard`. Mitigated: the
  edit is an **optional** ctor overload defaulting to today's self-meter behavior — every existing guard/refiner test
  compiles and passes unchanged; the shared path is opt-in at the root. Gate verifies additivity, not behavior change.
- **R-2 (wire-once meter + concurrency).** One `RunBudgetMeter` reset per `execute()` assumes runs are serialized
  (consistent with E2's wire-once `StartCrawlRun`). Concurrent `BuildWorkflowMap` runs would share one counter. MVP is
  single-flight; when the dashboard enables concurrent runs (E5/E7), switch to per-run construction via an injected
  factory. Recorded as the activation point — not built now (YAGNI).
- **R-3 (canonical-map "missing diff" misread).** A reviewer may expect a `collaborators.ts` change. §2 is the explicit
  resolution: post-hoc consumption in the detector IS the wiring; absence of the crawl-side diff is correct.
- **R-4 (embedding-client factory).** If `adapters/llm` lacks a Voyage client factory, #59 adds a thin one (adapter
  layer only). The E2E uses `FakeEmbeddingPort`, so the gate does not depend on a live embedding provider.
