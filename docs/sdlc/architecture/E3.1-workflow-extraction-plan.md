# E3.1 — Workflow Extraction from the State Graph (rule-based) — Architecture Plan

- **Ticket:** #54 (`mvp`, `type:feature`) · **Parent epic:** #3 (E3) · **Depends-on:** none
- **Mode:** plan (per-ticket; not a foundational ADR — refines within ADR-0001 §2.2/§3 and ADR-0004)
- **Governs:** ADR-0005 (E3 sameness spike, #53) is a _sibling_, not a dependency. This ticket is deterministic
  and must not consume any sameness/embedding/LLM output. Intent (#55) and naming/grouping (#56) are out of scope.

---

## 1. Approach & patterns

A **pure, deterministic extractor**: a single function over a finalized `StateGraph` producing `Workflow[]`,
with zero I/O, no driver, no LLM, no embeddings. It populates the **existing** `Workflow`/`WorkflowStep` domain
model (`packages/domain/src/models/workflow.ts`) — no domain edit expected (see §3).

Patterns applied by name:

- **Strategy** — entry-point identification and outcome identification are each injected predicates
  (`EntryPolicy`, `OutcomePolicy`) with rule-based defaults. Open/Closed: #56 (and a future LLM pass) extends
  behavior by supplying a different policy at the composition root, never by editing the traversal.
- **Builder** — `WorkflowStep[]` assembly is a small builder that owns `stepIndex` monotonicity and the
  terminal `edge = null` invariant, so the traversal core stays focused on path enumeration.
- **Pure function / DI** — the extractor is constructed with its policies + an `ExtractionConfig` value object
  (caps); it takes a `StateGraph` and returns `Workflow[]`. No ambient state, fully reproducible.

This is the simplest design that satisfies the standards: the graph fits in memory (it is one run's graph), so a
pure in-memory traversal is correct and avoids over-engineering (no streaming, no repository coupling in the
extractor itself — the use-case that _reads_ the graph from the port is #59's capstone, not here).

## 3. Domain model — the consumer contract (E4 + E8)

The existing model is **sufficient for this ticket — no domain edit.** Confirmed against the real types:

```ts
WorkflowStep { stepIndex: number; stateId: StateIdentity; edge: StateEdge | null; description: string }
Workflow    { id; name; description; steps: readonly WorkflowStep[]; isHiddenPath: boolean;
              inferenceConfidence: ConfidenceScore | null }
WorkflowMap { runId; workflows; finalisedAt }   // assembled by #59, not here
```

How #54 populates each field (and what it must **not** do):

| Field                 | E3.1 rule-based value                                                                                                                              |
| --------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| `id`                  | Deterministic, content-derived (stable hash of the ordered `stateId`+`edge.id` chain) — **not** random/UUID, or determinism (AC2) breaks.          |
| `name`                | A **rule-based placeholder** (`"Workflow N"` or `"<entry label> → <outcome label>"`). #56 overwrites with the LLM name. Documented as provisional. |
| `description`         | A rule-based one-liner (entry→outcome summary). **Do not overload** for purpose/group (OQ3 guard).                                                 |
| `steps`               | Ordered `WorkflowStep[]`; each non-terminal step carries the `StateEdge` taken; terminal step `edge = null`.                                       |
| `isHiddenPath`        | **`false`** always (FR5/#58 sets it).                                                                                                              |
| `inferenceConfidence` | **`null`** always (rule-only; AC6).                                                                                                                |

- **`WorkflowStep.description`** is rule-derived from the edge (`"tap"` / `"swipe"` + the node label), never LLM.
- **Additive-field flag (OQ3):** app-purpose and per-workflow feature-group are **out of scope** here and are an
  architect+E4 decision (additive optional fields vs a wrapper). **#54 must add no field and must not overload
  `description`/`name` to smuggle them.** If a developer feels the need to add a field, that is a signal to stop
  and route to arch-review — flag, don't silently extend.
- **One sanctioned additive type, in `application` not `domain`:** `ExtractionConfig` (the caps value object).
  It is application-layer config, not a domain concept, so it lives in `semantic/extraction/`, **not** in
  `packages/domain/src/models/`. No domain change ⇒ nothing for arch-review to approve on the model.

## 4. Traversal algorithm (implementable test-first)

Operate on an **adjacency index** built once from `graph.edges` (`Map<StateIdentity, StateEdge[]>`), with edges
within each adjacency list sorted by a **stable key** (`actionType`, then `actionPayload`, then `edge.id`) so
enumeration order is deterministic regardless of `edges[]` input order (AC2).

**Entry nodes (`ruleBasedEntryPolicy`):** the set of

- **graph sources** — nodes with in-degree 0 (no incoming edge), **plus**
- the **launch/root state** — the node first observed (min `firstSeenAt`, tie-broken by `id`) even if it later
  gains an incoming edge from a cycle, so a fully-cyclic graph still has a defined entry.

Entry set is sorted by (`firstSeenAt`, `id`) for stable iteration order.

**Outcome nodes (`ruleBasedOutcomePolicy`):** a node is an outcome iff

- it is a **sink** (out-degree 0, a terminal/leaf state), **or**
- it is in `graph.duplicatePathNodeIds` (E2 already flagged it as a convergence point — a meaningful outcome
  even if it has outgoing edges).

A path also yields a workflow when it is **forced to stop by a cap** (see below) — that truncated path's last
node is recorded as a _bounded_ outcome so nothing is silently dropped (AC: disconnected/orphan + cyclic).

**Enumeration — bounded DFS per entry:**

```
for each entry e (stable order):
  dfs(node=e, pathStates=[e], pathEdges=[], visitedOnPath={e}):
    if node is an outcome OR node has no unvisited outgoing edges:
        emit workflow(pathStates, pathEdges); return
    emittedChild = false
    for each outgoing edge (stable order), while caps allow:
        nextpathStates = pathStates+[edge.toId]
        if edge.toId in visitedOnPath:           # back-edge / cycle
            emit workflow up to here (cycle-closing path); continue   # do NOT recurse
        if len(nextpathStates) > maxPathLength:   # length cap
            emit truncated workflow; continue
        if workflowCount >= maxWorkflows: stop all enumeration (cap hit)
        dfs(edge.toId, nextpathStates, pathEdges+[edge], visitedOnPath ∪ {edge.toId})
        emittedChild = true
    if not emittedChild: emit workflow(pathStates, pathEdges)   # all children pruned ⇒ still a path
```

Key rules:

- **Cycle handling** uses a **per-path `visitedOnPath` set** (not a global visited): a node may legitimately
  appear in two _different_ workflows, but never twice in _one_ path. A back-edge closes the current path into a
  workflow and is not recursed — bounded, no infinite loop (AC3).
- **Dedupe trivial paths:** (a) a path of length 1 (entry == outcome, a lone node) is emitted only if that node
  is a genuine outcome/sink, so a mid-graph single node isn't spuriously a "workflow"; (b) workflows are
  de-duplicated by their **content-derived `id`** (§3) so two entries that funnel through an identical
  state+edge chain don't produce duplicate `Workflow` objects.
- **Combinatorial bound:** two caps from `ExtractionConfig` (no magic numbers, AC3) —
  `maxPathLength` (per-path depth) and `maxWorkflows` (total emitted). When `maxWorkflows` is hit, enumeration
  stops **deterministically** (entries processed in stable order) and the partial set is returned — graceful,
  not a crash. Defaults proposed: `maxPathLength = 40` (mirrors ADR-0004's `plateauWindow`/revisit scale),
  `maxWorkflows = 500`. Recorded in `defaultExtractionConfig`; tunable, gate-checked as config.
- **Disconnected components (AC5):** because we iterate **every** entry (every in-degree-0 node across all
  components), each component's reachable workflows are extracted. **Orphan surfacing:** after enumeration,
  compute the set of `graph.nodes` keys never visited by any path; the extractor returns them on its result
  envelope (`ExtractionResult { workflows, orphanStateIds }`) so they're surfaced, not dropped. (`orphanStateIds`
  is an extractor-internal return shape, not a domain-model field — #59 decides how/if the map exposes it.)

**Result shape (extractor public contract):**

```ts
interface ExtractionResult {
  readonly workflows: readonly Workflow[];
  readonly orphanStateIds: readonly StateIdentity[];
}
class WorkflowExtractor {
  extract(graph: StateGraph): ExtractionResult;
} // sync, pure
```

## 5. Interfaces / ports (SOLID / DI)

- **Depends on:** the domain **types** `StateGraph`, `StateNode`, `StateEdge`, `StateIdentity`, `Workflow`,
  `WorkflowStep` (imported from `@flowscout/domain`). **No port, no repository, no LLM dependency in #54.**
- **Note (ISP):** the extractor takes a `StateGraph` _value_, **not** the `StateGraphRepository` port. Reading
  the finalized graph from `StateGraphRepository.findByRunId` and assembling the `WorkflowMap` is the **#59**
  use-case (`BuildWorkflowMap`) job (FR7). Keeping the extractor port-free makes it trivially unit-testable
  (NFR2) and reusable — the right seam.
- **Exposes:** `WorkflowExtractor`, `ruleBasedEntryPolicy`, `ruleBasedOutcomePolicy`, `EntryPolicy`/`OutcomePolicy`
  interfaces, `ExtractionConfig` + `defaultExtractionConfig`, `ExtractionResult` — barreled through
  `application/src/index.ts` so #56/#59 import from the package boundary, not deep paths.
- **DI:** `new WorkflowExtractor(entryPolicy, outcomePolicy, config)`; a no-arg-friendly
  `defaultWorkflowExtractor()` wires the rule-based defaults. Composition happens at #59's root, not in #54.

## 6. Test strategy (coverage gate ≥85% application line+branch, NFR4)

Deterministic synthetic `StateGraph` fixtures (builders, no I/O, no LLM, no driver). Per-ticket `__tests__/`
only — no edits to shared `vitest.config` (E2 lesson, see ADR-0004 decomposition note).

Fixtures + cases:

1. **Linear** A→B→C: one workflow, 3 steps, terminal `edge=null`, `inferenceConfidence=null`, `isHiddenPath=false`.
2. **Branching** A→B, A→C: two workflows; stable order independent of `edges[]` insertion order.
3. **Convergent / duplicate-path** (A→C, B→C with C in `duplicatePathNodeIds`): C treated as outcome from both
   entries; both workflows emitted (no semantic flag — that's #58).
4. **Cyclic** A→B→A: bounded, terminates; back-edge closes a path; no infinite loop; respects `maxPathLength`.
5. **Cap saturation:** a graph engineered to exceed `maxWorkflows` → returns exactly the cap, deterministically,
   partial set, no throw.
6. **Empty graph** (no nodes): `{ workflows: [], orphanStateIds: [] }`, no throw (AC4).
7. **Single node, no edges:** sink ⇒ one trivial workflow (1 step, `edge=null`) **or** documented empty — pin the
   chosen behavior in a test (AC4). Decision: a lone node _is_ an outcome ⇒ one 1-step workflow.
8. **Disconnected components** (A→B and X→Y, no link): all four reachable; nothing dropped.
9. **Orphan node** (a node with no in/out edges that is not the launch node): surfaced in `orphanStateIds` (AC5).
10. **Determinism property:** run `extract` twice on the same fixture (and on a shuffled-`edges[]` copy) ⇒
    deep-equal `Workflow[]` incl. `id`s (AC2).
11. **Policy substitution:** an injected custom `OutcomePolicy` changes which workflows emit — proves Open/Closed
    - DI without touching the traversal.

Coverage targets: `WorkflowExtractor` + policies + builder ≥ 85% line **and** branch (each cap branch, the
back-edge branch, the empty/single-node branch, and the orphan branch are each hit by a named test).

## 7. Acceptance criteria (refined, Given/When/Then)

(Ticket ACs are sound; refinements in **bold**.)

1. **Given** a finalized `StateGraph`, **When** `WorkflowExtractor.extract` runs, **Then** it identifies entry
   node(s) = **in-degree-0 sources ∪ the min-`firstSeenAt` launch node**, outcome nodes = **sinks ∪
   `duplicatePathNodeIds`**, and emits one `Workflow` per distinct entry→outcome path, each with ordered
   `WorkflowStep[]` carrying `stateId`, the `edge` taken (**terminal `edge=null`**), and a rule-derived
   `description`.
2. **Given** the same `StateGraph` (incl. a copy with `edges[]` reordered), **When** `extract` runs, **Then**
   it returns deep-equal `Workflow[]` including content-derived `id`s (deterministic, stable ordering).
3. **Given** a cyclic graph, **When** `extract` runs, **Then** enumeration is bounded by
   `ExtractionConfig.maxPathLength`/`maxWorkflows` (config, **no magic numbers**), terminates, never explodes,
   and back-edges close a path rather than recurse.
4. **Given** an empty or single-node graph, **When** `extract` runs, **Then** it returns a valid result
   (`[]` for empty; one 1-step workflow for a lone node) — **never throws**.
5. **Given** a graph with disconnected components, **When** `extract` runs, **Then** every component's reachable
   workflows are extracted **and** unvisited nodes are surfaced on `ExtractionResult.orphanStateIds` — not
   silently dropped.
6. **Given** rule-only extraction, **When** each `Workflow` is built, **Then** `inferenceConfidence === null`
   and `isHiddenPath === false`, and **no app-purpose/feature-group field is added and `description`/`name` are
   not overloaded** to carry semantic data (deferred to #56/#58; OQ3 guard).

## 9. Risks

- **R-#54-1 — Path explosion on dense real graphs.** Mitigated by the two hard caps + per-path visited set; the
  cap-saturation test proves graceful truncation. Defaults (`maxPathLength=40`, `maxWorkflows=500`) are tunable
  config, surfaced for #59 to wire and for the eval to tune on a real app.
- **R-#54-2 — `name` placeholder mistaken for final.** Mitigated by documenting `name`/`description` as
  provisional rule-strings #56 overwrites, and by AC6 forbidding semantic overloading — keeps the E4 contract
  clean.
- **R-#54-3 — Determinism regressions** if any `Map`/`Set` iteration leaks into output ordering. Mitigated by
  explicit stable sorts on entries, outcomes, and adjacency, plus the AC2 shuffled-edges property test.
